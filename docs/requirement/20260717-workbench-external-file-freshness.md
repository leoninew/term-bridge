# Workbench 外部文件变更刷新与保存冲突
最后修改时间: 2026-07-17 15:19:31

Review status: Accepted

## Background

当前 Code Workbench 的远端文件系统 Provider 会缓存文件元数据、目录列表、文件内容和 ETag。用户通过终端、外部编辑器、Git 工作树操作或其他客户端直接修改物理工作区后，浏览器没有收到变更通知，因此 Explorer 和编辑器继续显示旧状态。

随后用户在浏览器保存同一文件时，浏览器会提交旧 ETag。后端检测到物理文件版本已变化并返回 `revision_conflict`；VS Code 将此呈现为 `EntryExists` 类保存失败。该拒绝行为保护了物理文件不被旧浏览器内容覆盖，但当前缺少及时刷新和清晰的冲突恢复体验。

## Goal

- 让本地和 Cloud Code Workbench 能感知工作区的物理文件变更，并同步刷新文件树、文件元数据和未脏编辑器内容。
- 保留乐观并发控制：外部变更绝不能被浏览器旧内容静默覆盖。
- 对存在本地未保存修改的编辑器，保留草稿并提供可恢复的保存冲突体验。
- 覆盖外部编辑器、终端命令、Git 丢弃/切换分支、其他客户端等变更来源。

## Non-goal

- 不解析或猜测终端命令语义；终端仍作为不透明 PTY 通道。
- 不通过周期性轮询模拟实时变更通知。
- 不自动覆盖脏编辑器、自动丢弃用户草稿或绕过 ETag/版本检查。
- 本需求不改变 Git 操作授权边界，也不扩展为完整协同编辑功能。

## User scenarios

1. 用户在 Workbench 打开文件或展开目录后，通过终端/外部编辑器修改、创建、删除或重命名工作区文件；浏览器应收到文件变更并更新 Explorer 与未脏编辑器。
2. 用户在浏览器中修改文件但未保存，随后物理文件被外部修改；浏览器必须保留草稿，保存时进入可恢复冲突流程，而不是覆盖外部内容。
3. 用户在 SCM 中执行丢弃、删除未跟踪文件或切换分支；受影响的文件树和编辑器不得继续使用旧缓存。
4. Cloud 用户仅能订阅自己有权访问的设备和工作区；重连、监听溢出或丢失事件时，浏览器必须保守地使整个工作区缓存失效并重新同步。

## Acceptance

- [ ] 物理文件创建、修改、删除和重命名能够从 Agent 传递到本地和 Cloud Workbench。
- [ ] 文件树不会将后端截断的目录列表伪装为完整目录。
- [ ] 外部变更后，Provider 失效受影响文件、子路径和父目录缓存，并通知 Workbench FileService。
- [ ] 修改前发起、修改后才返回的旧读请求不能重新写入旧缓存。
- [ ] 未脏文件的内容和元数据可刷新；脏编辑器的草稿不被自动替换。
- [ ] 使用过期 ETag 的保存仍被拒绝，并保留草稿进入可恢复冲突流程。
- [ ] SCM 会改变工作树的操作也会触发同一套文件缓存失效机制。
- [ ] 变更订阅、挂载和组件卸载均可释放资源；快速切换工作区不能让旧工作区覆盖当前 Provider。
- [ ] 缓存具备容量边界，长时间浏览大量文件不会无限占用浏览器内存。

## Open questions

- 文件监听事件的本地浏览器传输形式，以及 Cloud tunnel 中的订阅/推送帧细节，需要在实现阶段按现有连接模型确定。

## Decisions

- 已确认：后端 `revision_conflict` 是正确的数据保护行为，不能改为静默覆盖。
- 已确认：采用真实文件系统监听与类型化变更事件，不采用轮询或终端命令解析。
- 已确认：事件连续性无法证明时，采用工作区级保守失效和重新同步。
- 已确认：冲突恢复完全复用 `@codingame/monaco-vscode-api` / VS Code Workbench 原生 UI；若官方能力不足，先沟通并等待决策，不自绘替代 UI。
- 已确认：浏览器文件读取和写入继续使用既有 HTTP 文件 API；新增长连接仅传递只读物理文件变更事件。

## Risk

- 文件监听的跨平台行为、重命名配对和监听溢出需要以“重新扫描”作为安全降级。
- Cloud 推送通道需要继续遵守设备所有权、工作区授权和断线清理约束。
- Workbench 缓存失效必须避免覆盖脏模型，同时避免旧 in-flight 请求回填缓存。
