# M4 待办事项收口需求
最后修改时间: 2026-06-20 17:29:54

Review status: Accepted

## Background

当前项目实际实现已经推进到 M4 附近：

- 正式 CLI 入口已经确认为 `termbridge exec -- <command...>`。
- M1 CLI skeleton 已完成。
- M2 PTY Command Runner 核心能力已完成。
- M2.5 本地 Web terminal / workbench 已实现，但 large output、backpressure、history 写盘等风险仍需进入 M5 hardening。
- M3 Session / Workspace runtime model 已实现主体能力。
- M4 Local Product Surface 已实现大部分基础能力，但文档、验收清单和若干产品定义仍需收口。

当前项目文档需要统一呈现现行实现：命令执行入口为 `termbridge [options] exec -- <command...>`，M1-M3/M2.5 的完成状态和 M4/M5 边界需要与当前代码事实一致。README、设计说明、roadmap、TODO 等面向维护者或用户的文档应保持一致。

## Goal

完成 M4 进入 M5 前的收口工作：

1. 将 `docs/design.md` 中的正式 CLI 入口统一更新为 `termbridge [options] exec -- <command...>`。
2. 将 `docs/plan/20260617-roadmap-refresh.md` 中 CLI 示例和 M1-M4 状态更新为当前真实进展。
3. 检查并更新其他不再适用的文档内容，至少覆盖 README 中的当前使用方式；如发现 TODO、设计说明、计划文档中存在已失效阶段判断，也应同步修正。
4. 在 roadmap 中明确标记：
   - M1 已完成。
   - M2 核心已完成，hardening 风险进入 M5。
   - M2.5 已实现，Web terminal 风险进入 M5。
   - M3 主体已完成。
   - M4 处于主体完成 / 待收口状态。
5. 分析并记录 M4 剩余项，判断是否可以关闭 M4 并进入 M5。
6. 对 `recent command support` 和 `manual verification checklist` 两项进行解释：
   - 不实现显式 `recent` 命令或新 UX；当前 session metadata/listing/history 作为 M4 的基础 recent 能力。
   - manual verification checklist 中适合自动化的检查应补充单元测试；不适合自动化的交互场景才保留为人工验证项。
7. 保持 CLI-first 和 runtime ownership 边界：本地 Web/workbench 可以作为辅助产品面存在，但不改变 CLI 作为本地一等入口的定位。

## Non-goal

本次不做以下事项：

1. 不修改 Go/TypeScript 产品功能代码，除非是为 manual verification checklist 中可自动化事项补充单元测试。
2. 不实现新的 `recent` 命令、显式 recent UX 或 logs 命令。
3. 不解决 M5 hardening 问题，例如 process tree cleanup、Web backpressure、大输出、history flush 性能等。
4. 不进入 Gateway / M6 相关实现。
5. 不自动提交 Git commit。

## User scenarios

1. 作为项目维护者，我希望 roadmap 与当前代码事实一致，避免后续开发继续按旧 CLI 入口推进。
2. 作为开发者，我希望清楚知道 M1-M3/M2.5 哪些已经完成，哪些风险被转入 M5。
3. 作为产品决策者，我希望知道 M4 是否还有阻塞项，以及是否可以开始 M5 hardening。

## Acceptance

满足以下条件即可认为本需求完成：

1. `docs/design.md` 明确记录当前本地入口为 `termbridge [options] exec -- <command...>`。
2. `docs/design.md` 的设计原则与当前 CLI-first、exec 子命令和 local Web/workbench 边界一致。
3. `docs/plan/20260617-roadmap-refresh.md` 中 M1/M2/M2.5/M3/M4 状态与当前实现对齐。
4. `docs/plan/20260617-roadmap-refresh.md` 中 CLI 示例使用 `termbridge exec -- <command...>` 或 `termbridge --cwd <dir> exec -- <command...>`。
5. roadmap 中明确列出 M4 剩余项，并给出是否可进入 M5 的判断。
6. roadmap 或相关文档解释 `recent command support`：当前不实现显式 `recent` 命令或新 UX；M4 仅要求 session metadata/listing/history 能提供基础最近会话/命令可见性。
7. roadmap 或相关文档解释 `manual verification checklist`：适合自动化的检查应补充单元测试；无法稳定自动化的交互式场景才保留为人工验证项。
8. 若发现 manual verification checklist 对应的自动化测试缺口，应补充相应单元测试并运行相关测试。
9. README 等用户入口文档展示当前使用方式。
10. M5 hardening 风险没有被误标为已完成。

## Open questions

暂无需要用户确认后才能继续的阻塞问题。以下事项需要在实现时解释清楚：

1. `recent command support`：用户已确认不需要实现显式 `recent` 命令或新 UX；文档中应说明当前 session metadata/listing/history 作为 M4 的基础 recent 能力。
2. `manual verification checklist`：用户已确认适合写单元测试的检查应补单元测试；仅交互式、环境相关或难以稳定自动化的场景保留为人工验证项。
3. 文档一致性：README 等用户入口文档应展示当前命令示例，并与 design/roadmap 保持一致。

## Decisions

1. 正式 CLI 入口为 `termbridge exec -- <command...>`。
2. 用户入口文档需要展示当前使用方式，至少包括 README。
3. 不实现显式 `recent` 命令或新 UX；当前 session metadata/listing/history 作为 M4 的基础 recent 能力。
4. manual verification checklist 中适合自动化的检查应补充单元测试；不适合自动化的交互式场景保留为人工验证项。
5. 本次优先进行文档与 roadmap 收口，不处理 M5 runtime hardening 实现。
6. 本次流程采用轻量模式 / light。

## Risk

1. 如果文档未全面同步，用户入口、设计原则和 roadmap 可能呈现不一致的当前用法。
2. 如果把 M4 标记为完全完成，可能掩盖 manual verification checklist 中可自动化测试缺口。
3. 如果把 Web terminal 风险算作 M4 阻塞项，可能会拖延进入 M5；这些风险更适合转入 M5 hardening。
4. 如果 roadmap 中“本地 Web”定位表述不清，可能与 CLI-first 原则产生冲突。
