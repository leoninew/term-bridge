# 1440px 中等桌面屏幕布局适配需求
最后修改时间: 2026-07-13 23:55:34

## Review status

Accepted

## Flow mode / Stage

标准模式 / standard；需求 / Requirement 已接受，当前进入实现 / Implementation。

## Background

当前 Web UI 以桌面工作流为主，根节点设置了 `min-width: 1024px`，但各页面对 1440px 左右及以上桌面宽度的布局策略不完全一致。首页、仪表盘、快捷指令页和会话工作台分别使用不同的最大内容宽度、栅格断点、固定最小高度和 Splitter 约束；在 1440px 及以上桌面视口中，需要确保布局不会因内容宽度、空白分配或列比例而失衡。

初步盘点发现：

- 会话页采用侧边栏与终端工作台的水平 Splitter，侧栏比例受 `15%–25%` 约束，工作台仅有 `55%` 最小比例；需要在 1440px 左右宽度核对侧栏搜索/操作区、tab strip、终端和状态栏能否同时保持可用。
- Cloud landing 使用 `lg` 即启用的 `440px + 1fr` 双栏栅格，并设置 680px 内容最小高度和 520px 图片容器最小高度；该布局在中等桌面宽度可能出现图片区过大、首屏纵向内容密度不足或双栏比例失衡。
- 本地/云端 dashboard 和快捷指令页已使用内容最大宽度与多列 grid，但需要统一核查标题栏操作、长文本、卡片列数、间距和容器宽度在 1440px 下是否保持合理信息密度与截断语义。
- 登录、注册、密码重置、OAuth 回调、帮助和设置等辅助页面使用独立居中布局，也需确认其与应用全局最小宽度及视口高度约束兼容，但不应为此重做认证或业务流程。

## Goal

1. 对全部路由承载的用户页面及共享页面壳进行桌面宽度检查，基准视口为 `1440px` 宽，并确保布局在更宽桌面视口中保持稳定。
2. 优化已确认存在问题的布局，使页面在 `1440px` 及以上区间内不存在非预期横向溢出、核心操作不可达、关键内容被挤压到不可读、无意义的大面积留白或明显失衡的列宽。
3. 保持 `1440px` 及以上桌面布局、主题、路由和业务交互语义不回退；不为小于 `1440px` 的视口新增适配承诺。
4. 将中屏适配规则沉淀为清晰、复用的布局约束；优先使用既有 Tailwind CSS v4 工具类与全局样式 token，避免散落的页面级魔法宽度。
5. 在不改变产品信息架构的前提下，使会话工作台、首页、设备/本地仪表盘、快捷指令页和认证/辅助页在中屏下保持一致的容器宽度、间距层级和内容优先级。

## Non-goal

1. 不将产品改造成移动端或小于 `1440px` 的响应式应用；小于 `1440px` 的视口不在本任务的检查、优化或兼容性承诺范围内。
2. 不更改后端 API、认证、设备、会话、终端连接、快捷指令或数据加载的业务行为。
3. 不进行品牌重设计、替换 UI 库、全量改写页面结构或仅为视觉效果引入新的依赖。
4. 不以压缩字号、隐藏无关内容或制造不可发现的水平滚动作为解决布局问题的默认手段；内容优先级变化必须有明确的可用性理由。
5. 不执行未经明确授权的 Git 写操作。

## User scenarios

1. 用户在 `1440px` 及以上桌面视口打开会话页时，可以同时使用工作区侧栏、标签栏、终端区域和状态栏；侧栏控制不会遮挡或挤压终端到不可用尺寸，标签过多时仍使用现有滚动/溢出机制。
2. 用户在 `1440px` 及以上桌面视口打开 Cloud landing 时，文案、主操作和 hero 图形成稳定的视觉层级；不会因图片高度或双栏比例导致首屏出现无意义空白或重要操作被推离主要可视区域。
3. 用户在 `1440px` 及以上桌面视口查看本地或云端 dashboard 时，标题与操作保持同一行可读，列表的名称、状态、时间和路径在可用空间不足时以既有截断语义降级，而不是撑破容器。
4. 用户在 `1440px` 及以上桌面视口浏览、创建、编辑或排序快捷指令卡片时，卡片列数、最小阅读宽度、页面最大宽度与内容间距保持合理信息密度。
5. 用户在 `1440px` 及以上桌面视口打开登录、注册、验证、重置密码、OAuth 回调、连接、帮助和设置等辅助页面时，居中卡片及状态信息保持可读、无异常滚动和主题错位。

## Acceptance

- [ ] 覆盖路由表中所有用户可达页面；相同页面壳或同一组件复用的 local/cloud 变体可合并验证，但必须明确覆盖范围。
- [ ] 在 `1440px` 宽基准视口及更宽桌面视口下，页面根容器不产生由布局错误导致的横向滚动或内容裁切。
- [ ] 会话页的 Splitter、工作区侧栏、标签栏、终端区、状态栏和相关抽屉在 `1440px` 及以上宽度下可以同时正常显示和操作；不破坏现有侧栏拖拽、tab overflow、终端尺寸测量或抽屉行为。
- [ ] Cloud landing 的双栏布局、hero 图和首屏高度在 `1440px` 及以上宽度下保持均衡；必要时在不改变内容顺序的前提下设置对应的列宽、间距或高度策略。
- [ ] 本地/云端 dashboard、快捷指令页的内容容器、卡片 grid、标题操作区和长文本在 `1440px` 及以上宽度下保持一致的阅读密度、可达性和截断语义。
- [ ] 认证与辅助页面在 `1440px` 及以上宽度下仍保留居中、可读、主题正确的表单或状态区域。
- [ ] 布局规则使用语义明确的桌面断点或集中 CSS 规则；不引入无上下文的重复像素常量，不将校验或响应式判断散落到业务逻辑中。
- [ ] `1440px` 及以上布局、暗色/浅色主题、路由和现有交互不发生功能回归；小于 `1440px` 的布局不在本次回归范围内。
- [ ] 实现阶段至少通过前端 typecheck、lint、format 检查和与本次修改相关的测试；验证阶段记录 `1440px` 及以上实际视口检查结果及无法自动化覆盖的手动检查项。

## Open questions

暂无需要用户确认的未决事项。

适配基准按 CSS viewport 宽度理解：以 `1440px` 为主要检查点，并验证更宽桌面视口。小于 `1440px` 的视口由用户明确排除，不作为本任务的设计、实现或验证依据。若后续浏览器实测发现某一业务页面在 `1440px` 及以上区间有特定内容量导致的问题，会在实施中将该场景列为明确改动项，而非盲目统一压缩所有页面。

## Decisions

1. 本任务采用标准模式 / standard：影响多个路由页面、共享 layout、会话工作台与视觉回归验证，需要先形成计划再实施。
2. 本任务是独立的新任务，只新增与 `medium-screen-layout-adaptation` 相关的阶段文档，不修改历史 SpecFlow 文档。
3. 范围以 CSS viewport `1440px` 为主，并覆盖更宽桌面视口；不把物理显示器分辨率与浏览器可用视口混为一谈，小于 `1440px` 的视口明确不在范围内。
4. 会话工作台、Cloud landing、local/cloud dashboard、快捷指令、认证和辅助页面均在检查范围；共享 `AppHeader`、全局样式、对话框与抽屉按实际影响纳入。
5. 优先以现有 Tailwind CSS v4、CSS token、组件结构和 Reka UI 能力实现，不新增 UI 体系。

## Risk

1. 页面间存在不同布局范式；若只调整单页宽度，可能造成容器和间距标准继续漂移，因此 Plan 阶段需先识别可共享的布局规则和必须保留的页面差异。
2. 会话页承载终端，调整侧栏或终端区域可能影响 xterm 列数、初始尺寸测量、tab overflow 和拖拽 Splitter 行为；必须以真实页面验证而非仅静态 CSS 审查。
3. 文本长度随语言、设备名称、路径和命令变化；布局修复需要确认已存在的 `min-w-0`、`truncate` 和滚动策略仍能正确表达信息优先级，不能只针对短英文文本调样式。
4. 仅运行 typecheck/lint 无法发现可视回归；验证阶段需要通过浏览器在 `1440px` 及以上目标视口检查关键路由和交互状态，并记录未能自动化的状态。
5. `min-width: 1024px` 是既有实现细节，不是本任务的兼容性承诺；除非影响 `1440px` 及以上的实际问题，否则不修改该全局约束。
